AI Rules Playbook

An AI rule doc is a file an agent loads while it works in part of the code. A good one stops the agent from making a mistake it cannot see coming. A bad one teaches it a wrong fact with full confidence.

Guidelines

Four groups. Cite a rule by its ID in a review comment, for example "this line breaks G6".

What a rule doc is for

G1.A doc states the correct pattern, and the chapter decides what that pattern is.

An agent that writes a doc only sees the files it has open. It sees one feature do something and writes "every page does X", because that is how documentation usually sounds. Counting across the code catches a doc that copied one feature. The count still does not decide the pattern. A person who owns the area does.

Example:A doc told everyone to put a feature's pages in a pages/ folder. Only one feature did that. Five others kept their pages flat, and the one feature was the wrong one.

G2.A consumer that does it wrong never becomes an exception line or an example.

Code that breaks a rule does not make the rule false. If the doc adds "except in feature Y", the agent reads feature Y as allowed and copies it. Keep a short list of the known wrong consumers in your area, and give it to every agent that writes or reviews your rules.

G3.Keep traps, rules and decisions. Delete descriptions of what the code visibly does.

A trap is behaviour an agent cannot see in the code, which costs an hour when missed. A rule says what to do or avoid. A decision records a choice and why. A description only retells the code. The test: if an agent learns it by opening one file or running one search, it does not belong in the doc.

Descriptions are the sentences that go false. The code changes and nobody updates the retelling.

Keep (trap):A new service file has to be imported by hand. A file nobody imports is never mounted, and its route answers 404.
Delete (description):A service file exports one definition or an array of them.

Writing a line that stays true

G4.No line numbers. Name the file and the identifier.

A line number is correct until the next commit above it. A function name survives most edits, and when it does not, a search finds the break.

G5.No pasted copies of real files. A code block shows a shape.

A block labelled with a real file path is a copy, and a copy goes stale without any warning. Write the smallest shape that shows the pattern, and point at the file to copy.

Example:A 30-line copy of a vendor file was already wrong: it called a function it no longer imported.

G6.No counts and no lists of who does what. Write the condition that decides.

A list of pages, routes or helpers is true today and wrong the day someone adds one more. The condition behind the list stays true.

Instead of:The search, cart and checkout pages report errors to the shared logger.
Write:A page that can fail reports its errors to the shared logger.

G7.At most one example file per rule, and it comes from a correct consumer.

One file to copy helps. Three files turn into a list (G6). An example from a wrong consumer teaches the wrong pattern (G2).

G8.Write "every", "always", "only" or "never" only after you checked for the counterexample.

These words make a line sound certain, so an agent trusts it most. A single counterexample in the code makes the whole line false.

G9.Prove every claim about behaviour by reading the code.

A claim that sounds logical from the shape of the code is a guess. A reviewer who reads it makes the same guess and agrees, so reviews do not catch it.

Example:"A wrong parameter name makes the call 404" sounded right, because the URL is built from the call. The code sends only the values, so a wrong name puts the value in the wrong parameter and no error appears.

G10.Describe the current state only. No history, no plans.

"Moved from", "previously" and "used to" describe history, and git already has it. "Will", "yet" and "planned" describe a future that may never come. Both go stale, and both confuse an agent about what is true now.

G11.Plain English and short sentences.

Many developers read English as a second language, and an agent follows a plain sentence more reliably than a clever one. One fact per sentence. Explain a pattern in plain words before you name it.

Where a line lives

G12.Each fact lives in one doc. Point to it instead of repeating it.

Two copies of a fact drift apart, and then the agent loads both and has to pick one. Before you add a line, search the other docs. If a doc that loads on the same files already says it, write a pointer.

G13.Put a trap in the doc that loads on the file where the mistake gets made.

A doc is path scoped: it loads only when the agent opens a matching file (in Claude Code, the paths: list in its frontmatter). A trap in a doc that never loads on the right file never helps anyone. Check which docs load for a file before you decide where a line goes.

Example:The trap "never run prettier over these files" lived in a doc that loads only on translation files. Nobody editing a component ever saw it.

G14.Never narrow a doc's loading to save context.

A rule that fails to load where it matters costs far more than a few kilobytes of context. Narrow a path scope only when you are sure the doc has nothing to say to those files. After any change, check that the doc still loads on the file where the trap's mistake gets made. Check it with a script, not by hand: a hand check covers only what someone remembers to check, and a script checks every doc every time.

Example:A short script in the repo reads the paths: list of every rule doc, flags a pattern that matches no tracked file, and, given one file, lists the docs that load for it. In Node it needs one dependency, multimatch, which also handles brace patterns.

Fixing and reviewing

G15.A false line is deleted by default.

Making a false line true almost always means adding its exception or its caveat, so every fix makes the doc longer and harder to keep true. Keep a line only when it is a trap. Then write its shortest true version.

G16.When you overturn a claim, search every doc for the old claim in the same change.

The old answer stays in every other file that repeated it, and those files still look approved. Nothing shows the gap until an agent loads two docs that disagree.

G17.Measure each changed doc against the main branch.

Compare the word count per doc. A fix makes a doc longer only when it adds a real trap. Also check that every file path in the changed lines exists.

G18.Review rules by running commands, with a fresh agent. Then check the reviewer.

A review that only reads the doc opens the example the doc names, and that example agrees, because the line was written from it. The reviewer has to search and count. Use a fresh agent and not a copy of the one that wrote the lines, because a copy carries the same context and defends it. Before you apply a finding, check its evidence yourself: reviewers are wrong sometimes too.

G19.Review the changed lines in every rules MR, and audit everything only now and then. Stop when the findings turn into taste.

A reviewer's job is to find something, so a fresh one always will. What matters is the kind of finding. Another round is worth it only while reviews still find false claims or rules that do not load where they matter. The code proves those. When the findings become wording, or a new reviewer disagrees with the last one, stop.

G20.Bloat means repeated or unneeded text, not a large file.

A long doc full of real traps is fine. A short doc that retells the code is not. Cut repetition and descriptions. Never cut a trap to reach a length.

Review loop

A fixed set of steps that checks rule docs against the code and fixes what the owner approves. A critic agent looks for false lines, a refuter agent tries to disprove each finding, and nothing changes until you say go. It works after any rules task: a first draft, new rules added to existing docs, or a review of someone's MR.

Your prompt has two parts:

  1. Your task, in your own words. What you want done and which rule docs it touches.
  2. The loop, pasted under the task. It runs when the task is done, or right away if the task is only a review, on every rule doc line the task added, changed or names. Keep the steps as they are.

Example task: "Add a rule for src/payments/ to docs/ai/payments.md: a new payment status also needs its translation key." Then paste the loop under it.

review-loop.txt 
Step 0. Check what you know.
Do the task above first. If the task is only a review, start here.
You need four things: which docs and lines to review, how a doc loads (for example a `paths:` list, and the command that lists which docs load for one file), which code is the correct pattern, and how to run commands in this repo. If the task does not say one of them, ask me and wait. Never guess which docs to review.

Step 1. Critic.
Start one new subagent, never a copy or fork of this session, because a copy carries the context that wrote the lines and defends them. Give it only this brief and the four things from step 0. It reads and reports, and never edits.

  A finding is one of three things:
  - a false line that makes an agent write wrong code
  - a missing line, where an agent following today's docs writes broken code and nothing warns them
  - a rule that does not load on the file where the mistake gets made
  Prove every finding by running commands (search, count, read the code, the loading command). Never infer from how the code looks.
  Code that breaks a rule does not make the rule false. Do not report it.
  Every finding names: the doc and the line, quoted briefly; the command and its output; the file an agent edits where it gets hurt, and what it would write wrong there; the action, which is "delete", "add one sentence" with the sentence and the doc it goes into, or a one-sentence rewrite.
  Out of scope: wording, style, repeated text, and bugs in the code itself.
  "No findings" is a correct result. Do not fill the report to look thorough.

Step 2. Refuter.
For each finding, start another new subagent, all of them in parallel. Give each one the quoted line, the command and its output, and the file where an agent gets hurt. Leave out the critic's explanation, so the refuter checks the code and not the critic's argument. Its job is to disprove the finding:
  - Attack both halves: that the line is false, and that an agent editing the named file would write wrong code.
  - Use at least two different sources of evidence, for example the code path, the config, the git history, or the code that calls it.
  - Every statement needs a file and an identifier it read itself, in this session.
  - Return REFUTED, STANDS or UNDECIDABLE, with the evidence.
Drop every REFUTED finding. An UNDECIDABLE finding comes to me as a question.

Step 3. Report, then wait.
Show me the findings that stand, in three groups: wrong lines, missing lines, rules that do not load. Every item names the file where the damage happens and carries your recommendation, so "go" is a complete answer. If a finding undoes an earlier decision, for example by putting back a line an earlier fix removed, say so. Then wait. Edit nothing until I answer.

Step 4. Fix.
Apply only what I approved, in this session, not in a subagent.
  - Delete a false line by default. Rewrite it only when the true version prevents a mistake the deletion would not, and then in its shortest form.
  - No line numbers, no counts, no lists of which files do something, no pasted copies of real files.
  - When you overturn a claim, search every doc for the old claim and fix it everywhere in the same pass.
  - Never narrow a doc's loading to save context.
Then check every changed doc: its word count against the main branch, that every path in the changed lines exists, and that the doc still loads on the file where the mistake gets made.

Step 5. Another round, or stop.
Run steps 1 to 4 again, on the lines you just changed only. Another round is worth it only while the critic still finds lines that make an agent write wrong code, or rules that do not load where they matter. Stop when the findings turn into wording, or when a new critic disagrees with the last one, and tell me which one stopped you.

Do not commit.

When to run it

  • After a first draft, before the MR (G18).
  • On every MR that touches a rule doc, on its changed lines only (G19).
  • On a chapter's whole doc set, only now and then. Stop when the findings turn into wording.

Large codebases

A prompt that says "scan the repo and write our rules" writes one feature's habit up as a universal rule. Work area by area instead.

  1. Start with the shared layers. Draft the rules for the code every feature uses first, such as infrastructure, the HTTP client and error handling. Feature docs can then point to those rules instead of repeating them.
  2. One area per session. Pick one area, run your prompt, answer its questions, and ship that doc in its own MR. The next area starts in a fresh session.
  3. Split a big area across subagents. Each subagent reads one sub-area and returns candidates with evidence. The main session merges them, removes repeats, and asks the owner. Subagents never write the doc, so the decisions stay in one place.
  4. Keep the owner in the loop. Where the code disagrees with itself, your task should tell the agent to ask the owner which side is the correct pattern, instead of picking the majority. Skipping that question is how a majority vote in the code becomes the rule.
